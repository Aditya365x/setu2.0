# Real-Time Disaster Early-Warning & Resource Coordination Platform

## 1. Project Objective

The proposed platform is a **real-time disaster-management and resource-coordination system** designed for situations such as floods, cyclones, landslides, and other emergencies.

The central objective is:

> **Collect dynamic information about people requiring help, combine it with pre-existing disaster-response resources, and give authorities a live operational map that helps them prioritize and allocate resources.**

The platform should focus less on having a large number of features and more on demonstrating one strong workflow:

**Citizen reports emergency → location appears live on command-centre map → incident is prioritized → suitable resource is identified → authority assigns resource → assignment is visualized on the map.**

---

# 2. Core System Concept

The system consists of two fundamentally different types of information.

## A. Static / Preloaded Resource Data

These are resources that already exist and are available for disaster response.

Examples:

- Rescue teams
- NDRF/local rescue units
- Shelters
- Medical facilities
- Supply warehouses
- Boats
- Ambulances
- Food/water stocks

These resources are **not created dynamically when an incident occurs**.

They are entered into the system beforehand and stored in the database.

Example:

```text
Rescue Team R17
Location: 22.5726, 88.3639
Capacity: 8 people
Status: AVAILABLE
Equipment: Boat
```

---

## B. Dynamic Incident Data

These are reports generated by citizens during an actual disaster.

Examples:

- People trapped
- Flooded houses
- Medical emergencies
- People requiring evacuation
- Roads blocked
- Buildings damaged

These records are created continuously.

Example:

```text
Incident #104

Location: 22.5731, 88.3650
Type: Flood
Severity: CRITICAL
People affected: 5
Description: People trapped on rooftop
Status: UNASSIGNED
```

This distinction is fundamental:

```text
                 SYSTEM DATA
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
      RESOURCES              INCIDENTS
          │                     │
       STATIC                DYNAMIC
          │                     │
     Preloaded             Created live
```

# 4. Citizen Reporting Application

The citizen application should be deliberately simple.

During an emergency, the user should be able to submit a report in approximately **10–20 seconds**.

The app should not become a social-media-style application. Its main purpose is to capture accurate emergency information quickly.

## 4.1 Home Screen

The primary screen should contain:

```text
DISASTER HELP

[ REPORT EMERGENCY ]

View Local Alerts
My Reports
Nearby Shelters
Emergency Contacts
```

The **Report Emergency** button should be the dominant action.

---

# 5. Emergency Report Form

The report form should capture the minimum information needed by the command centre.

## 5.1 Location

The application automatically obtains the user's GPS coordinates.

Example:

```text
Location:
22.5726, 88.3639

[Use Current Location]
```

The user should also be allowed to adjust the location manually on a map if the GPS position is inaccurate.

---

## 5.2 Disaster Type

Provide predefined options rather than requiring users to type everything.

Possible options:

- Flood
- Cyclone
- Landslide
- Fire
- Building collapse
- Medical emergency
- Other

Example:

```text
What is happening?

[ Flood ]
[ Cyclone ]
[ Landslide ]
[ Medical Emergency ]
[ Building Collapse ]
[ Other ]
```

---

## 5.3 Severity

The user selects:

- LOW
- MEDIUM
- HIGH
- CRITICAL

Suggested interpretation:

```text
LOW      → Situation exists but immediate assistance is not required
MEDIUM   → Assistance is required
HIGH     → Immediate assistance required
CRITICAL → People are trapped / immediate danger
```

This severity becomes an important input for the allocation algorithm.

---

# 6. People Affected

The user specifies the approximate number of people requiring help.

Example:

```text
How many people need help?

[-]  5  [+]

Additional conditions:

[ ] Children
[ ] Elderly
[ ] Injured people
[ ] People with disabilities
```

This information is useful because a resource should not be selected only based on distance.

For example:

```text
Incident:
20 people

Team A:
2 km away
Capacity = 5

Team B:
4 km away
Capacity = 30
```

The system should select **Team B**, even though it is farther away, because Team A does not have enough capacity.

---

# 7. Description

The citizen can provide a short description.

Example:

```text
People trapped on rooftop.
Water level is increasing.
```

The description helps authorities understand the situation beyond numerical fields.

# 15. Offline Map

The map should continue functioning even when internet connectivity is unavailable.

The recommended approach is:

**OpenStreetMap data + offline MBTiles + MapLibre**

The base map can contain:

- Roads
- Rivers
- Buildings
- Bridges
- Major landmarks
- Administrative boundaries
- Other geographic features

For a hackathon prototype, download only the geographic region relevant to the demonstration instead of trying to store the entire country at high detail.

Example:

```text
Offline Map
    ↓
West Bengal
    ↓
Kolkata + surrounding disaster-prone area
```

The offline map is the **static geographic foundation**.

---

# 16. Static and Live Map Layers

The map should be thought of as two separate layers.

## Static Layer

Downloaded beforehand:

```text
Roads
Rivers
Buildings
Bridges
Boundaries
```

## Live Layer

Created by the application:

```text
🔴 Victims / incidents
🔵 Rescue teams
🟢 Shelters
🟣 Supply warehouses
```

Therefore:

```text
OFFLINE BASE MAP
        +
LIVE INCIDENT DATA
        +
STATIC RESOURCE DATA
        ↓
COMMAND-CENTRE MAP
```

The map itself does not need to be modified whenever a new person reports an emergency.

Only the **live data layer changes**.

# 19. Live Incident Creation

The most important real-time workflow is:

```text
Citizen fills form
        ↓
GPS location obtained
        ↓
POST /api/incidents
        ↓
Backend validates data
        ↓
Database stores incident
        ↓
WebSocket event generated
        ↓
Command centre receives event
        ↓
React state updates
        ↓
Map receives new marker
        ↓
🔴 Incident appears
```

The command centre should **not require a page refresh**.

# 21. Live Location Updates

The system can also support changing victim locations.

For example, a person moves to another building.

The citizen app sends:

```text
PUT /api/incidents/104/location
```

with the updated GPS coordinates.

The backend updates the incident.

A WebSocket event is sent to the command centre.

The map moves:

```text
BEFORE

🔴


AFTER

      🔴
```

No map refresh is required.

This is useful when people are moving during an evacuation.

# 24. Resource Allocation Engine

This is the **most important technical feature for the judges**.

The platform should not merely display incidents.

It should help authorities decide:

> **Which resource should handle which incident?**

The first version can use nearest-suitable-resource matching.

---

# 25. Allocation Algorithm

For every unassigned incident:

```text
1. Calculate incident priority

2. Find available resources

3. Check resource type

4. Check capacity

5. Calculate distance

6. Rank suitable resources

7. Recommend the best resource

8. Allow authority to assign it
```

Example:

```text
Incident #104
CRITICAL
5 people

Available teams:

R17 → 2.4 km → Capacity 8
R21 → 5.8 km → Capacity 12
R09 → 3.1 km → Capacity 4
```

R09 is unsuitable because:

```text
Capacity 4 < People 5
```

Therefore:

```text
R17 → Best match
```

---

# 26. Priority Calculation

A simple scoring model is sufficient for the prototype.

Example:

```text
Severity Score
LOW      = 1
MEDIUM   = 3
HIGH     = 5
CRITICAL = 10
```

The overall priority can consider:

```text
Priority =
    Severity
    +
    People affected
    +
    Waiting time
    +
    Vulnerable people
```

This does not need to be an advanced AI model.

The objective is to demonstrate a logical, explainable allocation mechanism.

---

# 27. Capacity-Aware Allocation

Distance should not be the only factor.

Example:

```text
Incident:
20 people

Team A:
2 km away
Capacity = 5

Team B:
4 km away
Capacity = 30
```

The system should choose Team B.

Therefore:

```text
BEST RESOURCE =
distance
+
capacity
+
severity
+
resource type
+
availability
```

This makes the system much more realistic.

---

# 28. Shelter Allocation

The same logic can be applied to shelters.

Example:

```text

Shelter A:
2 km
Available capacity = 30

Shelter B:
4 km
Available capacity = 150
```

Allocation:

```text
30 → Shelter A
70 → Shelter B
```

This can be displayed in the command centre.

# 33. IMD / Disaster Alert Integration

The platform can receive external disaster/weather alerts.

Example:

```text

     ↓

     ↓
Affected Geographic Region
     ↓
```

# 34. SMS Fallback

In areas without mobile internet/data, a citizen may still have cellular connectivity.

SMS can therefore act as a fallback.

A predefined message format can be used.

Example:

```text
HELP FLOOD 5 22.5726 88.3639
```

The backend interprets it as:

```text
Type: Flood
People: 5
Location: 22.5726, 88.3639
```

and creates a normal incident record.

Therefore:

```text
App report
     ↓
          INCIDENT
     ↑
SMS report
```

Both eventually enter the same incident-processing pipeline.

---

# 35. IVR Fallback

IVR means **Interactive Voice Response**.

A citizen calls a disaster-response number.

The system can ask:

```text
"Press 1 for Flood"
"Press 2 for Cyclone"
"Press 3 for Landslide"
```

Then:

```text
"How many people need help?"

Citizen → presses 5
```

The system collects the information and creates an incident.

Conceptually:

```text
Phone Call
    ↓
IVR
    ↓
Incident Created
    ↓
Backend
    ↓
Command Centre
```

For the hackathon MVP, a simulated IVR integration can be sufficient if a real telecom integration is too complex.

---

# 36. Offline Disaster Operation

The system should continue to provide useful geographic functionality even if internet connectivity is lost.

The recommended architecture is:

```text
OpenStreetMap
      ↓
Offline Map Data
      ↓
MBTiles
      ↓
MapLibre
      ↓
Local Map
```

Then the application's own incident/resource data is layered over it.

Important distinction:

```text
OFFLINE MAP
    +
LIVE/LOCAL APPLICATION DATA
    ↓
OPERATIONAL MAP
```

The base geographic map does not need to be downloaded again when a new incident appears.

# 42. The Central Value Proposition

The project should not be presented as:

> "We have a citizen app, a map, SMS, weather alerts, shelters, AI, and many other features."

Instead, present it as:

> **"We created a live disaster-response command centre where citizen reports dynamically appear on an offline map, are prioritized based on urgency and affected population, and are matched with available rescue resources in real time."**

Everything else supports this central workflow.
